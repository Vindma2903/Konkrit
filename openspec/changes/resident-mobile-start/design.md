# Дизайн-решения

## Стек приложения

| Что | Выбор | Зачем |
|---|---|---|
| Каркас | Expo (актуальный SDK), TypeScript strict | Один инструментарий для iOS и Android |
| Навигация | `expo-router` (файловая) | Простые стеки, глубокие ссылки позже |
| Серверное состояние | TanStack Query | Кэш, повтор, статусы загрузки |
| Клиентское состояние | Zustand | Сессия, черновик заявки, шаг онбординга |
| Формы и валидация | `react-hook-form` + `zod` | Правила валидации в одном месте, переносимы в общий пакет |
| Иконки | `react-native-svg` | Иконки макета — это stroke-SVG 24×24, перерисовываем 1:1 |
| Шрифт | `@expo-google-fonts/montserrat` (500, 600, 700, 800) | Как в макете |
| Токены | `expo-secure-store` | Хранение access/refresh токенов |
| Тесты | Jest + `@testing-library/react-native` | Валидация, маски, поведение экранов |

Версии пакетов не фиксируем в спеке: ставим актуальные при реализации и фиксируем в lock-файле.

## Токены (из макета P2-StyleA и экранов)

текст акцента `#A82E2E`, мягкий акцент `#FDECEC`, граница `#E6E7E8`, неактивная кнопка
`#E6E7E8` / текст `#6B7077`, ошибка `#B3261E`, успех `#1E6B3A`, рамка радио `#C4C7CB`.
Радиусы: карточка 20, поле 14, кнопка и чип 999. Высоты: поле 52, кнопка 56, ячейка кода

## Правила UI-предпочтений заказчика, которые затрагивают эти экраны

- Поля идут друг под другом, без двух колонок.
  **Отклонение макета:** на экране привязки «Квартира» и «Лицевой счёт» стоят в одну строку.
  По правилу делаем столбиком; макет надо поправить.
- Списки из многих значений — выпадающее поле/лист снизу. У нас такие поля («Категория»,
  «Адрес») рисуются как кнопки-выпадашки, как в макете.
- Роль («Собственник», «Жилец») — два значения, остаются чипами как в макете.
- Активная вкладка не тёмная. Переключатель «Телефон / Почта» в макете — белая плашка
  на сером фоне; оставляем как в макете (не тёмный).
- Ссылки согласия: цвет `#A82E2E`, жирные, подчёркнутые.
- Кнопка внизу закреплена; при длинном содержимом скролл всего экрана, у кнопки тень.

## Слой данных

`ApiClient` — интерфейс с методами, которые соответствуют контракту (`api/openapi.yaml`):

- `requestCode({ channel, value })` → `{ retryAfterSec }`
- `verifyCode({ channel, value, code })` → `{ accessToken, refreshToken, user, hasResidency }`
- `searchHouses({ query })` → `House[]`
- `submitResidency({ houseId, apartment, account, role, verification })` → `{ status: 'pending' }`
- `suggestCategory({ text })` → `{ categoryId, name } | null`
- `createRequest({ categoryId, description, residencyId })` → `{ id }`

Сейчас подключён только `mockApi`: задержки 300–800 мс, фиксированные тестовые данные
(только для `__DEV__`; в продакшн-сборку мок не попадает). Подключение реального клиента —
замена одной зависимости.

## Подсказка категории (S2)

Локальный классификатор в `mockApi.suggestCategory`: по словам-ключам («отоплен», «батаре» →
«Отопление» и т. д.). Подсказка появляется, когда описание ≥ 10 символов, категория не
выбрана и пользователь перестал печатать 500 мс. Реальную категоризацию сделает бэкенд
(ТЗ 3.1), контракт тот же.

## Состояние и сессия

Токены в `expo-secure-store`. После `verifyCode`: если `hasResidency = false` —
онбординг (выбор дома → привязка), иначе — главная (в этом изменении заглушка).
Шаг онбординга и выбранный дом лежат в Zustand и переживают возврат «Назад».

## Тестирование

Юнит: маска телефона, схема валидации заявки, правила кнопки. Компонентные: код
(автопереход между ячейками, вставка из буфера, таймер), форма заявки в состояниях S1–S4.
Типы: `tsc --noEmit`. Линт: `eslint`. Ручная проверка на эмуляторе — отдельная задача.
