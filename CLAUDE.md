## Разработка через спеку

Если запрос добавляет или меняет поведение — **сначала спека, потом код**. Спека
лежит в `openspec/changes/<name>/`: `proposal.md`, `specs/<capability>/spec.md` (дельта),
`design.md`, `tasks.md`.

1. Сначала уточни запрос: только вопросы, которые меняют объём работы.
2. Артефакты готовы — **стоп**. Не пиши код в том же ответе, даже если запрос просил
   «сделать». Спека и код — разные шаги.
3. Реализация — по `tasks.md`, в ветке, с тестами там, где есть проверяемое поведение.
4. После всех задач — ревью всего диффа (корректность, безопасность, тяжёлая синхронная
   работа). Критичное чинится сразу; некритичное — чинится или откладывается с согласия
   пользователя. Молча проигнорированных находок быть не должно.
5. Готовую спеку переносим в архив.

Спрашивать пользователя нужно только про настоящую неоднозначность, необратимое и
**push / PR / слияние**.

**Можно пропустить спеку** только для: опечатки, правки бага в 1–2 строки без изменения
контракта и поведения, значения в конфиге, комментария/README. Если правка тянет
архитектурное решение (новая таблица, новый эндпоинт, фоновая задача, внешняя
интеграция) — спека всегда, даже на «быстро поправить».

## Существующие данные — всегда часть решения

Любое изменение, которое меняет то, как данные создаются, копируются или связываются,
**обязано ответить: «а что с тем, что уже лежит в базе»**. «Правка только на будущее» —
осознанный выбор, который нужно обосновать.

- Главное — не потерять данные и не испортить консистентность; это важнее чистоты схемы.
- К изменению поведения идёт миграция данных. Состояние «часть по старым правилам, часть по
  новым» — источник неуловимых багов.
- Удалять только то, что доказано не используется — запросом, не предположением.
- Применённую миграцию не редактируем: только новая. Миграции обратно совместимы
  (только добавляем; удаление и переименование — отдельным релизом позже).

## Не маскируй проблемы в UI — чини причину, не вид

Если данные лишние, дублирующиеся или мёртвые — не фильтруй их из выдачи ради вида.
Правильный fix — не создавать лишнее (условие раньше записи) либо убрать по тому же
событию, которое сделало объект ненужным.

## Git

- Работаем **веткой от `main`**, имя по сути изменения. Параллельная работа — в git
  worktree, не в общем каталоге. Перед коммитом проверь текущую ветку.
- **Push, PR и слияние — только по явной команде пользователя.** Агент не мёрджит и не
  пушит в `main`.
- Коммит — сразу после готового и проверенного изменения.

## Конвенции

- **Язык.** Общение с пользователем — по-русски, всегда. Комментарии, тексты интерфейса и
  сообщения ошибок — по-русски, идентификаторы — по-английски.
- **Коммиты:** сообщение на русском; тело — что и почему.
- **Секреты** (`.env`, ключи) не читать без нужды, не печатать и не коммитить: в
  диагностике — длина ключа, код ответа, первые байты.
- Тексты и стиль интерфейса — по правилам UI-предпочтений «Конкрит» (skill
  `konkrit-ui-preferences`): поля формы, выпадающие списки, вложения, переключатели, ссылки.
